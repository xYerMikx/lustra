## 1. Контекст и проблема

Основной способ записи к частному бьюти-мастеру в Минске сегодня — **директ в Instagram/Telegram**. Из этого вытекают проблемы:

**Для клиента**
- Нет единого места, где видно свободное время у разных мастеров «на завтра рядом с домом».
- Цены не сравнить: они в сторис, в закреплённых, в переписке или «по запросу».
- Непонятно, как выглядят реальные работы (лента перегружена репостами и рекламой).
- Легко забыть про запись → неявка или неловкая отмена в последний момент.

**Для мастера**
- Запись ведётся в блокноте/заметках/Google-календаре, параллельно с 5 диалогами в директе.
- Двойные записи, забытые брони, отсутствие истории клиента («какой цвет делали в прошлый раз»).
- Неявки: клиент не пришёл, окно простаивает.
- Нет входящего потока новых клиентов, кроме сарафана и Instagram-алгоритма.

**Гипотеза продукта.** Мастер получает бесплатный, действительно удобный журнал записи (со slot-management, ручной записью «из директа», заметками по клиенту и напоминаниями в Telegram) → мастер сам приводит своих клиентов в сервис → у сервиса появляется наполненный каталог с реальными слотами → каталог начинает приводить мастеру новых клиентов. Ключевой цикл роста строится через **мастера**, а не через рекламу для клиентов.

## 2. Конкуренты и позиционирование

| Продукт | Что делает | Слабые места, которые мы используем |
|---|---|---|
| **beautygo.by** | Свежий (2025–2026) агрегатор мастеров по Беларуси | Только что запустился → каталог полупустой, бренд ещё не закреплён. Окно возможностей 6–12 месяцев |
| **DIKIDI Online** | Огромная функциональность записи + CRM, много мастеров в СНГ | Перегруженный устаревший UI, ощущение «системы для салона», слабая витрина-портфолио, слабый мобильный UX |
| **YCLIENTS** | Профессиональная CRM для салонов | Дорого и тяжело для мастера-одиночки, это не агрегатор для клиента |
| **Instagram / Telegram DM** | Фактический стандарт записи | Нет календаря, нет напоминаний, нет сравнения цен. **Это наш реальный конкурент** |
| **Barb.by, локальные сайты салонов** | Запись в конкретный салон | Не агрегируют частных мастеров |

**Позиционирование:** «Instagram-эстетика витрины + рабочий журнал записи. Красиво для клиента, бесплатно и удобно для мастера, напоминания — в Telegram, где все и так сидят.»

**Ключевые дифференциаторы MVP**
1. Витрина-портфолио уровня Instagram (крупные фото, галереи, быстрая загрузка) — против «таблиц» у DIKIDI.
2. Telegram-напоминания обеим сторонам (24 ч / 2 ч) → меньше неявок.
3. Ручная запись «из директа» в 3 тапа: мастер продолжает получать заявки в Instagram, но журнал ведёт у нас (это то, что мешает конкурентам: у них ручная запись спрятана глубоко).
4. Личная ссылка/QR мастера (`/m/anna-nails`) — годится для bio в Instagram и для сарафана; SEO-страница индексируется и приводит трафик.

## 3. Роли и персоны

**Мастер (основной драйвер).** Анна, 27, маникюр, работает в арендованном кабинете, 6–10 клиентов в день, 90% записей — Instagram-директ. Телефон в руках весь день, ноутбук — редко. **Требование: мобильный интерфейс без компромиссов.**

**Клиент.** Катя, 24, ищет мастера по району и цене, смотрит фото работ, хочет записаться ночью без переписки и получать напоминание.

**Администратор (мы).** Модерация мастеров и портфолио, верификация, разбор жалоб, ручное наполнение каталога на старте.

*Вне скоупа MVP:* салон с несколькими сотрудниками и ролевой моделью, администратор салона, филиалы.

## 6. Ключевые пользовательские сценарии

**S1. Мастер приходит с лендинга (5 минут до готового профиля).**
`Лендинг → «Я мастер» → регистрация (email+пароль) → онбординг-визард: 1) имя, фото, район, 2) первая услуга (шаблоны: «Маникюр комбинированный, 90 мин, 60 BYN»), 3) график («будни 10:00–20:00»), 4) 3 фото работ → предпросмотр публичной страницы → «Скопировать ссылку для Instagram» → баннер «Привяжи Telegram, чтобы не пропускать записи».`
Профиль публикуется сразу, но с меткой `pending_review`; в каталоге появляется после модерации (до 12 ч), личная ссылка работает мгновенно — чтобы мастер сразу мог кидать её клиентам.

**S2. Мастер записывает клиента из директа.**
`Календарь (день/неделя) → тап по свободному окну → «Записать вручную» → услуга (автоподстановка длительности) → имя + телефон клиента (или выбор из ранее записанных) → канал (Instagram/Telegram/телефон/оффлайн) → приватная заметка («аллергия на гель X») → сохранить.` Окно становится `booked` с меткой «вручную». Если у гостя указан телефон и он позже зарегистрируется с этим номером — записи привязываются к аккаунту (v1.1).

**S3. Клиент бронирует.**
`Каталог → фильтр «Маникюр» + «Фрунзенский» + «до 70 BYN» + «завтра» → карточка мастера → портфолио → услуга → выбор слота → (регистрация/вход, если гость) → комментарий «хочу короткую длину» → «Забронировать» → статус «Ожидает подтверждения» → уведомление в Telegram обеим сторонам → мастер подтверждает → напоминание за 24 ч и 2 ч.`

**S4. Отмена/перенос.** Клиент может отменить сам не позднее 12 ч до записи (порог настраивается мастером); позже — только запросом («Отменить и написать мастеру»). Мастер может отменить/перенести всегда, с обязательной причиной, клиент мгновенно получает уведомление.

**S5. Отзыв.** Через 2 часа после `completed` клиенту приходит запрос в Telegram/на сайте: звёзды + текст + до 3 фото. Отзыв публикуется после автопроверки (стоп-слова) и попадает в рейтинг.

## 7. Функциональные требования

Формат: `[приоритет] описание → реализация → критерии приёмки (AC)`. Оценки — в идеальных днях разработки одного разработчика с AI-ассистом.

### F-01. Аутентификация и роли · P0 · 3 д
- **Описание.** Регистрация email+пароль, вход, выход, восстановление пароля, выбор роли на входе (`client` / `master`), один аккаунт = одна активная роль (клиент может позже «стать мастером» — создаётся master-профиль на том же user).
- **Реализация.** NestJS: `argon2id` для паролей, access JWT (15 мин, в памяти клиента) + refresh JWT (30 дней, httpOnly Secure SameSite=Lax cookie на домене `.<домен>`), ротация refresh-токенов с хранением хеша в `refresh_tokens`, отзыв при смене пароля. Подтверждение email — письмо со ссылкой (Resend), но **не блокирует** работу (мягкая верификация: без подтверждения нельзя опубликовать master-профиль). Rate limit на `/auth/*`: 10 запросов/мин/IP.
- **AC.** Регистрация ≤3 полей; повторный вход не требует пароля 30 дней; смена пароля инвалидирует все сессии; попытка входа с чужим refresh-токеном → 401 и отзыв цепочки; пароль ≥8 символов проверяется на клиенте и на сервере.

### F-02. Профиль мастера и онбординг · P0 · 4 д
- **Описание.** Поля: имя/бренд, `slug` (латиница, уникальный, редактируемый один раз), аватар, обложка, короткий заголовок («Мастер маникюра, 5 лет»), описание (до 1000 символов), районы работы (1–3 из справочника Минска), тип локации (`salon` / `home_studio` / `client_home`), адрес-ориентир (без точного адреса до подтверждения брони), телефон, Instagram, Telegram, годы опыта, языки.
- **Реализация.** Пошаговый визард (4 шага, прогресс, сохранение черновика после каждого шага в `localStorage` + PATCH на сервер). Статусы профиля: `draft → pending_review → published → hidden/banned`. Публичная страница доступна по ссылке уже в `pending_review`, в каталоге — только `published`. Автогенерация `slug` из имени с транслитерацией и суффиксом при коллизии.
- **AC.** Прохождение онбординга ≤5 минут на телефоне; после шага 4 показывается предпросмотр и кнопка копирования ссылки/QR; незаполненный обязательный блок блокирует публикацию с понятным чек-листом («добавьте 1 услугу», «добавьте 3 фото»).

### F-03. Услуги и цены · P0 · 3 д
- **Описание.** Услуга: категория (справочник: ногти, брови/ресницы, волосы, макияж, косметология, депиляция, массаж, тату/пирсинг), название, длительность (шаг 15 мин), цена в BYN, тип цены (`fixed` / `from` / `range`), описание, флаг «требует предварительной консультации», сортировка, активность.
- **Реализация.** CRUD с шаблонами популярных услуг по категории (ускоряет онбординг и нормализует названия для фильтров и SEO). Длительность услуги = основа расчёта слотов. Опциональный `buffer_after_min` (уборка/дезинфекция).
- **AC.** Изменение цены не меняет цену уже существующих броней (в брони фиксируются `price_snapshot` и `duration_snapshot`); деактивация услуги не удаляет историю; у мастера минимум 1 активная услуга для публикации.

### F-04. Портфолио · P0 · 4 д
- **Описание.** До 60 фото на мастера (лимит MVP), привязка фото к услуге/категории, подпись, порядок, обложка профиля; клиент смотрит галерею с лайтбоксом и свайпом.
- **Реализация.** Прямая загрузка в объектное хранилище по presigned URL (обход API-сервера), затем POST метаданных. На клиенте перед загрузкой: ресайз до max 2000 px и конвертация в WebP через `canvas` (уменьшает трафик мастера в 5–10 раз на мобильном). На сервере — валидация MIME (magic bytes), лимит 8 МБ, генерация 3 размеров (320/720/1440) и `blurhash` для placeholder-а. Модерация: автоматическая проверка (лимиты, дубликаты по хешу) + ручная в админке; NSFW-скрининг — v1.1.
- **AC.** Загрузка 10 фото с телефона по 4G ≤60 с; галерея не вызывает CLS (фиксированные aspect-ratio + blurhash); удаление фото удаляет объекты из хранилища (soft-delete 30 дней).

### F-05. График работы и генерация слотов · P0 · 6 д (самая рискованная фича)
- **Описание.** Мастер задаёт недельный шаблон (по дням: интервалы работы, до 3 интервалов в день + перерывы), горизонт бронирования (по умолчанию 30 дней), минимальный лид-тайм (по умолчанию 3 ч), шаг сетки слотов (15/30/60 мин), буфер между записями, порог самостоятельной отмены клиентом.
- **Реализация.** Свободные слоты **не хранятся в БД**, а вычисляются: `доступность(шаблон + исключения) − брони(pending|confirmed) − блокировки − лид-тайм`, с шагом сетки под длительность выбранной услуги. Всё во `Europe/Minsk`, хранение в БД — `timestamptz` в UTC. Кэш ответа `/availability` 60 с с инвалидацией по событиям брони.
- **AC.** Ответ `/masters/:id/availability?service=&from=&to=` <200 мс p95 для горизонта 30 дней; переход на летнее/зимнее время не ломает сетку (тест на 26.10 и 29.03); слот с длительностью услуги 90 мин не предлагается, если до конца рабочего интервала осталось 60 мин.

### F-06. Управление слотами и заметки · P0 · 3 д
- **Описание.** Мастер может: заблокировать окно/день («обед», «учёба», «отпуск»), разблокировать, добавить исключение к графику на дату, изменить существующую бронь (время/услуга/цена), добавить приватную заметку к брони и к клиенту, отметить `completed` / `no_show`.
- **Реализация.** `blocked_slots` (диапазон + причина) и `schedule_exceptions` (нерабочий день / особые часы). Календарь: день (таймлайн) и неделя (сетка), drag-to-block на десктопе, тап-и-выбор на мобильном, оптимистичные обновления.
- **AC.** Блокировка мгновенно убирает слот из публичной выдачи; попытка заблокировать окно с существующей бронью → предупреждение с предложением перенести/отменить; приватные заметки не отдаются клиентскому API ни в каком ответе (проверяется тестом).

### F-07. Ручная запись мастером · P0 · 3 д
- **Описание.** Создание брони мастером за клиента с указанием источника (`instagram`, `telegram`, `phone`, `walk_in`, `other`), имени, телефона, необязательного email, заметки. Клиент может не иметь аккаунта («гость»).
- **Реализация.** Модель `guest_client` (принадлежит мастеру: имя, телефон, заметки) + `booking.source = manual`. Автокомплит по ранее созданным гостям и по клиентам, которые ранее записывались. Мастер может пометить окно как занятое **без клиента** (это `blocked_slot`, не бронь) — важно, чтобы не мусорить статистикой.
- **AC.** Создание ручной брони ≤3 действий после тапа по окну; ручные брони видны в статистике отдельно от онлайн-броней; телефон гостя нормализуется в `+375XXXXXXXXX`.

### F-08. Каталог и фильтры · P0 · 5 д
- **Описание.** Список/сетка мастеров с фильтрами: категория и конкретная услуга, район (мультивыбор), диапазон цены, «есть свободное время: сегодня / завтра / на этой неделе / выбрать дату», рейтинг ≥4, тип локации, сортировки (рекомендуемые, дешевле, дороже, рейтинг, ближайшее окно).
- **Реализация.** Server-side фильтрация в Postgres: `pg_trgm` для поиска по имени/услуге, составные индексы, курсорная пагинация. Фильтр «есть окно завтра» — по денормализованному полю `master_profiles.next_available_at`, обновляемому воркером при изменении броней/графика (иначе фильтр будет считать доступность по всем мастерам и упадёт по времени). Состояние фильтров синхронизируется с URL (`?service=manicure&district=frunzenskiy`) → шарится и индексируется.
- **AC.** Первая выдача (24 карточки) <500 мс p95; фильтры работают без полной перезагрузки; пустая выдача предлагает ослабить фильтр («убрать район» / «расширить цену»).

### F-09. Публичная страница мастера · P0 · 4 д
- **Описание.** Hero (обложка, аватар, имя, рейтинг, район, «свободно завтра в 14:00»), услуги с ценами, портфолио, отзывы, блок «о мастере», кнопка «Записаться» (sticky на мобильном), ссылки на соцсети, QR для шаринга.
- **Реализация.** Next.js ISR (`revalidate 300` + `revalidateTag('master:<id>')` из вебхука API при изменении профиля), JSON-LD `LocalBusiness`/`BeautySalon` + `AggregateRating` + `Offer` + `Review`, OG-картинка генерируется динамически (`@vercel/og`) из аватара и имени. URL: `/m/[slug]`.
- **AC.** Страница индексируется (проверка в Search Console), LCP <2.5 с на 4G, OG-превью корректно рендерится при отправке ссылки в Telegram/Instagram DM, кнопка записи видна без скролла на iPhone SE.

### F-10. Бронирование клиентом · P0 · 5 д
- **Описание.** Флоу: услуга → дата → слот → комментарий → подтверждение. Гость может выбрать слот до регистрации; регистрация вклинивается перед подтверждением и не теряет выбор.
- **Реализация.** Черновик брони в `sessionStorage`, после логина — автопродолжение. Создание брони в транзакции с защитой от двойной записи (Postgres `EXCLUDE` constraint по пересечению диапазонов, см. §11). Статус по умолчанию `pending`; мастер может включить «автоподтверждение» → сразу `confirmed`. Немедленные уведомления обеим сторонам, постановка отложенных напоминаний в очередь.
- **AC.** Две одновременные брони на один слот → одна успех, вторая получает 409 и обновлённый список слотов; бронь создаётся ≤4 экранов; лид-тайм и горизонт мастера соблюдаются на сервере (клиентская валидация не является источником истины).

### F-11. Отмена и перенос · P0 · 3 д
- **Описание.** Клиент отменяет сам до порога (по умолчанию 12 ч), позже — «запрос на отмену». Мастер отменяет/переносит с причиной. Все переходы статусов логируются.
- **Реализация.** Машина состояний: `pending → confirmed → completed`, из `pending|confirmed` → `cancelled_by_client|cancelled_by_master|no_show`; переходы только вперёд, история в `booking_events`. Перенос = отмена + создание новой брони со ссылкой `rescheduled_from_id` (сохраняет аналитику). Отмена снимает отложенные задачи-напоминания.
- **AC.** Напоминание не приходит по отменённой брони (регрессионный тест); счётчик отмен клиента виден мастеру (защита от «отменяльщиков»); мастер обязан указать причину при отмене.

### F-12. Кабинет клиента · P0 · 2 д
- **Описание.** «Мои записи» (предстоящие/прошедшие), детали брони (мастер, услуга, цена, адрес-ориентир, контакты, кнопка «в Telegram мастеру»), избранные мастера, профиль, привязка Telegram.
- **AC.** Предстоящая запись видна на первом экране после входа; точный адрес мастера открывается только для `confirmed` брони.

### F-13. Отзывы и рейтинги · P0 · 4 д
- **Описание.** Двусторонние отзывы после `completed` (мастер отметил визит завершённым), окно 14 дней, по одному отзыву с каждой стороны. Клиент → мастер: оценка 1–5 обязательна, текст до 800 символов, до 3 фото. Мастер → клиент: оценка необязательна — можно звёзды, только комментарий или оба; без аккаунта клиента отзыв недоступен. Мастер может один раз ответить на отзыв клиента. Публичный рейтинг мастера в каталоге и на `/m/[slug]` считается только по опубликованным оценкам клиентов, как среднее арифметическое звёзд (`Σоценок / n`). Комментарий без оценки в среднее не входит. У клиента свой рейтинг из оценок мастеров (карточка «Отзывы о вас»).
- **Реализация.** Автомодерация (стоп-слова, ссылки, контакты) → `published` или `pending_review`. Агрегаты мастера и клиента пересчитываются в транзакции публикации. Снимок `serviceTitle` хранится на отзыве и показывается в каталоге/профиле. Пометка `verified` — все отзывы в MVP только по факту записи.
- **AC.** Нельзя оставить отзыв без завершённой записи (проверка на сервере); отзыв клиента появляется в JSON-LD и в карточке каталога вместе с услугой; мастер может оставить комментарий без звёзд; удаление/модерация отзыва пересчитывает нужный агрегат.

### F-14. Telegram: привязка и уведомления · P0 · 5 д
- **Описание.** Привязка аккаунта к Telegram (кнопка «Подключить Telegram» → deep link `t.me/<bot>?start=<nonce>`). Уведомления: новая бронь (мастеру), подтверждение/отмена (клиенту), отмена клиентом (мастеру), напоминание за 24 ч и 2 ч (обоим), запрос отзыва (клиенту). В сообщениях — инлайн-кнопки «Подтвердить»/«Отменить»/«Перенести» для мастера.
- **Реализация.** `Telegraf` внутри NestJS-процесса (webhook, не polling), `BullMQ` + Redis для отложенных и повторяемых задач, `jobId = booking:<id>:reminder:24h` для идемпотентности и отмены. Ретраи с экспоненциальной задержкой, лог всех отправок в `notifications` (для дедупликации и отладки). Уважение настроек тишины (не отправлять 23:00–08:00 кроме срочного, напоминание за 2 ч — исключение).
- **AC.** Привязка ≤2 тапов; напоминания приходят в ±2 мин от расчётного времени; повторный запуск воркера не дублирует сообщения; блокировка бота пользователем не роняет отправку (ошибка 403 → флаг `telegram_blocked`, fallback на email в v1.1).

### F-16. Лендинг, юридические страницы, SEO-инфраструктура · P0 · 5 д

### 8.2 Почему NestJS, а не Express

Ты просил «прослойку для бэкенда» и попросил выбрать. Беру **NestJS на Fastify-адаптере**:

- **Задачи проекта структурно совпадают с сильными сторонами Nest:** много планировщиков и фоновых задач (`@nestjs/bullmq` из коробки), WebSocket-чат в v1.1 (`@nestjs/websockets` — тот же DI, те же guard-ы), Telegram-webhook, cron-задачи (`@nestjs/schedule`) для `next_available_at`, авто-`completed`, запросов отзывов.
- **DI и модульность** дают внятную границу для самой сложной части — `AvailabilityService` / `BookingService`: их можно юнит-тестировать без HTTP и без БД, подменяя репозитории. В Express это выродится в самописный контейнер или в 800-строчные контроллеры.
- **Guards/Interceptors/Pipes** = единообразные авторизация, роли, валидация Zod, логирование, идемпотентность. В Express каждый такой аспект — это ещё один самодельный middleware.
- **OpenAPI-спека** генерируется из декораторов (`@nestjs/swagger`) → типизированный SDK для Next.js и Astro без дублирования.
- **Fastify-адаптер** снимает главный аргумент против Nest (производительность): по throughput он в 2–3 раза быстрее Express-адаптера, а холодный старт не важен, т.к. API живёт как долгоживущий процесс, а не в лямбде.
- **Цена:** больше бойлерплейта и порог входа выше, чем у Express. Для одноразового CRUD это был бы overkill; для сервиса с расписаниями, очередями, чатом и платежами в перспективе — это экономия времени начиная со второго месяца.

*Fastify «в чистом виде» (без Nest)* остаётся разумной альтернативой, если приоритет — минимум абстракций; тогда каркас придётся собрать руками (DI, валидация, модульность, swagger). Express не рекомендую: он не даёт ничего из перечисленного и в 2026-м это по сути легаси-выбор.

### 8.3 Что осознанно НЕ берём

- **Supabase Auth / RLS как основа доступа** — бизнес-логика уходит в БД-политики, теряется переносимость и тестируемость; Supabase используем как managed Postgres + Storage.
- **tRPC** — API должен быть доступен и Astro-лендингу, и потенциальному мобильному клиенту, и боту; REST + OpenAPI-SDK универсальнее.
- **GraphQL** — лишняя сложность для 30 ручек.
- **Микросервисы** — один Nest-монолит с модулями; выносим воркер отдельно только когда упрёмся в CPU.
- **Kubernetes** — VPS/PaaS с Docker Compose достаточно на порядок дольше, чем нам нужно.

**Домены и SEO-маршрутизация.** Держим **один домен** — это критично для SEO (весь ссылочный вес и Search Console в одном хосте). Реализация: проект Astro владеет доменом, а в его `vercel.json` прописаны rewrites на деплой Next.js:

```json
{
  "rewrites": [
    { "source": "/catalog/:path*", "destination": "https://app-<project>.vercel.app/catalog/:path*" },
    { "source": "/m/:path*",       "destination": "https://app-<project>.vercel.app/m/:path*" },
    { "source": "/app/:path*",     "destination": "https://app-<project>.vercel.app/app/:path*" },
    { "source": "/admin/:path*",   "destination": "https://app-<project>.vercel.app/admin/:path*" }
  ]
}
```

Плата — один дополнительный сетевой хоп (~20–40 мс) на страницах приложения; лендинг остаётся чистой статикой на CDN. *Fallback-вариант, если rewrites окажутся проблемой:* приложение на `app.<домен>`, а публичный каталог и страницы мастеров всё равно остаются на основном домене (их обслуживает Next через rewrite) — публичные SEO-страницы с основного домена уводить нельзя.

**Sitemap.** Астро генерирует `sitemap-pages.xml`, Next — динамический `sitemap-masters.xml` (из БД, обновляется при публикации мастера); на основном домене лежит `sitemap.xml`-индекс, ссылающийся на оба.

## 11. Логика доступности и бронирования (ядро продукта)

> **Замещено.** Решение изменено: слоты **материализуются** в `TimeSlot` (намерения → проекция), бронирование идёт по протоколу `hold → confirm` с пессимистичной блокировкой гранул. См. `docs/TECH-DESIGN.md` §6, §10, §11. Блок ниже — версия 0.1 (расчёт на лету), оставлен для истории.

### 11.1 Расчёт свободных слотов

Свободные слоты вычисляются на лету, а не хранятся:

```
availability(master, service, dateRange):
  1. base    = недельный шаблон WorkSchedule, развёрнутый на даты диапазона (local Europe/Minsk)
  2. base    = применить ScheduleException (день выключен / особые часы заменяют шаблон)
  3. busy    = Booking(status in pending|confirmed) ∪ BlockedSlot за диапазон
  4. free    = base − busy                       // интервальная разность
  5. need    = service.durationMin + max(service.bufferAfterMin, master.bufferAfterMin)
  6. slots   = для каждого свободного интервала: сетка с шагом master.slotStepMin,
               оставить точки start, где [start, start+need) ⊆ интервал
  7. отфильтровать start < now + master.minLeadTimeMin
     и start > now + master.bookingHorizonDays
  8. вернуть [{ startsAt(UTC ISO), endsAt }]
```

**Правила времени.** Хранение — `timestamptz` (UTC). Шаблон графика — в локальных минутах суток; развёртка в UTC делается через `date-fns-tz` с зоной `Europe/Minsk`. Belarus с 2011 г. живёт в постоянном UTC+3 без переходов, но зону всё равно закладываем через tz-библиотеку (не хардкодим `+03:00`) и покрываем тестом на случай изменения законодательства и на корректность для мультигорода в v2.

**Производительность.** Один SQL-запрос на диапазон (брони + блокировки), интервальная арифметика в памяти; ответ кэшируется в Redis на 60 с по ключу `avail:<masterId>:<serviceId>:<from>:<to>` с инвалидацией по событиям `booking.*`, `schedule.*`, `block.*`.

### 11.2 Создание брони (конкурентность)

```
POST /bookings  (idempotency-key в заголовке)
  BEGIN;
    SELECT ... FROM "MasterProfile" WHERE id = :masterId FOR SHARE;   -- фиксируем настройки
    -- пересчитать слот на сервере: услуга активна, время кратно сетке,
    -- попадает в рабочий интервал, не нарушает lead time / горизонт
    INSERT INTO "Booking" (...) VALUES (...);   -- EXCLUDE-констрейнт = финальный арбитр
  COMMIT;
```
- Нарушение `booking_no_overlap` → Postgres `23P01` → API отдаёт **409 CONFLICT** + актуальный список слотов, UI показывает «это время только что заняли, вот ближайшие».
- Идемпотентность: заголовок `Idempotency-Key` (UUID из клиента) хранится 24 ч в Redis → повторный тап по «Забронировать» не создаёт дубликат.
- После коммита (в `AFTER COMMIT`-хуке, не внутри транзакции): события `booking.created` → немедленные уведомления + постановка задач `reminder:24h`, `reminder:2h`, `autocomplete` в BullMQ; инвалидация кэша доступности; пересчёт `nextAvailableAt`.

### 11.3 Машина состояний брони

```
pending ──confirm(master|auto)──▶ confirmed ──complete(master|cron)──▶ completed ──review(14д)
   │                                  │
   ├─cancel(client, до cutoff)        ├─cancel(client, до cutoff)
   ├─cancel(master, +причина)         ├─cancel(master, +причина)
   ├─expire(cron: не подтверждена     └─no_show(master, после времени начала)
   │  за 12 ч или начало < now)
   ▼
cancelled_by_*
```
- Любой переход пишется в `BookingEvent` (кто, когда, из какого статуса).
- `completed` ставится мастером вручную либо cron-задачей через 3 ч после `endsAt` (мастера часто забывают отмечать; это критично для отзывов и статистики).
- Отмена/перенос **удаляет отложенные задачи** по `jobId` — иначе клиент получит напоминание об отменённой записи (главный источник багов в подобных сервисах).
- Перенос = `cancelled_by_master` + новая бронь с `rescheduledFromId` (чтобы не потерять аудит и не считать это отменой в метриках).

## 13. Дизайн-система

**Арт-направление:** «тихая роскошь бьюти-студии» — тёплая нюдовая бумага, много воздуха, крупная типографика с засечками, фотография как главный носитель эмоции. **Никаких сине-пурпурных градиентов**, никаких неоновых glow-эффектов, никаких «AI-SaaS»-стеклянных карточек. ### 13.1 Токены

Полный набор — `docs/TECH-DESIGN.md` §23. Шкалы задаются **числами**, а не размерными суффиксами (`--radius-8`, `--text-16`, `--spacing-12`, `--shadow-1`, `--duration-250`) → утилиты Tailwind читаются как `rounded-8`, `text-16`, `gap-12`, `shadow-1`. Цвета — семантические имена (`--color-accent`, `--color-surface-2`, `--color-text-2`), значения палитры считаем черновиком и финализируем после первых живых экранов: имена токенов при этом не меняются, поэтому перекраска не затронет компоненты.

Базовая палитра: фон `#FAF7F4`, поверхность `#FFFFFF`, блоки `#F1E8E1`, границы `#E4D8CF`, текст `#221A17` / `#6E5F58` / `#9C8C84`, акцент (терракота) `#C25E52` → `#A94A40`, шампань `#C6A15B`, шалфей `#8A9A7B`, глина `#6B4E42`, статусы `#4C8B6A` / `#D08A3A` / `#9E2B3F`.

Тёмная тема — v1.1 (тот же набор токенов, значения через `[data-theme="dark"]`: фон `#17110F`, поверхность `#211A17`, акцент светлее на 12%).

### 13.2 Типографика

- **Display:** `Playfair Display` (есть кириллица) — H1/H2, цены на карточках, цитаты. Fallback: `Prata`, `Lora`.
- **Text/UI:** `Inter` (или `Manrope` — оба с полной кириллицей) — body, кнопки, формы, таблицы.
- Шкала (mobile → desktop, `clamp()`): H1 32→56, H2 26→40, H3 20→28, body 15→16, caption 13.

| Где | Что | Реализация |

## 15. Нефункциональные требования

**Безопасность**
- Argon2id (m=19456, t=2, p=1), пароль ≥8 символов, проверка на утечки через k-anonymity API (опционально).
- JWT: access 15 мин (`Authorization: Bearer`), refresh 30 дней в httpOnly+Secure+SameSite=Lax cookie, ротация с детекцией повторного использования → отзыв всей цепочки.
- CSRF: для cookie-ручек (`/auth/refresh`, `/auth/logout`) — double-submit токен; остальные ручки только Bearer.
- `helmet`, строгий CORS-allowlist (домен лендинга + домен приложения + localhost), CSP (`script-src 'self'`, без `unsafe-inline` — nonce для инлайнов), HSTS.
- Rate limit: `/auth/*` 10/мин/IP, `POST /bookings` 20/час/пользователь, публичный каталог 120/мин/IP.
- Валидация всех входов Zod, whitelist полей на выходе (DTO-маппинг, чтобы `masterNote` физически не мог утечь), явные тесты на IDOR (клиент A не читает бронь клиента B).
- Загрузка файлов: presigned URL с ограничением `content-length` и `content-type`, проверка magic bytes на воркере, отдача файлов только с CDN-домена хранилища.
- Секреты — только в переменных окружения провайдера и `.env.local` (в `.gitignore`), `git-secrets`/`gitleaks` в CI.
- Sentry со скрабингом PII (email, телефон, токены).

**Персональные данные (Беларусь, Закон №99-З «О защите персональных данных»)**
- Обязательный чекбокс согласия при регистрации со ссылкой на политику (не предустановлен), отдельное согласие на публикацию фото работ.
- В политике: перечень собираемых ПД (email, имя, телефон, фото, история записей, Telegram chat_id), цели, сроки хранения, права субъекта, порядок отзыва согласия, контакт ответственного лица.
- Реализовать в продукте: экспорт своих данных (JSON) и удаление аккаунта (soft-delete + анонимизация через 30 дней, брони обезличиваются, но остаются в статистике мастера).
- Уведомление субъекта об инциденте, назначение ответственного за защиту ПД, журнал обращений.
- **Юридическая вычитка политики и оферты для мастеров обязательна до публичного запуска** — формулировки в репозитории считаем черновиком.

**Надёжность**
- Аптайм-цель 99.5% (это ~3.6 ч/мес — реалистично для одного VPS + managed БД).
- Бэкапы Postgres: ежедневные + PITR (Supabase), **проверенный restore-прогон** на staging до запуска; экспорт хранилища раз в неделю.
- Graceful shutdown, healthchecks, автоперезапуск (Docker `restart: unless-stopped`), очереди переживают рестарт (Redis persistence AOF).
- Идемпотентность всех воркеров уведомлений.

**Доступность (a11y)**
- Контраст ≥4.5:1 для текста (проверить `--champagne` на белом — использовать только для декора и иконок, не для текста).

## 16. Инфраструктура, окружения, деплой

Решено: всё самохостим на одном VPS под Docker, репозиторий и CI — GitHub. **Выбор прод-Postgres (self-hosted в контейнере vs managed Neon/Supabase) отложен до среза 7–8** — код от этого не зависит (Prisma + стандартные расширения, переезд = смена `DATABASE_URL` + `pg_dump/restore`).

| Окружение | Лендинг | web (Next) | API | БД / Redis |
|---|---|---|---|---|
| local | `pnpm dev` (4321) | `pnpm dev` (3000) | `pnpm dev:api` (3333) | Docker Compose: Postgres 16 + Redis |
| CI (на PR) | build + Lighthouse | build | vitest + supertest | Testcontainers локально, **Neon free** ветка на PR для миграций/e2e |
| staging | Cloudflare Pages preview | второй compose-стек на том же VPS (`staging.<домен>`) | тот же стек, лимиты `cpus 0.5 / mem 512m` | `lumira_staging` + Redis db 1 — **0 € сверху** |
| prod | Cloudflare Pages (статика, коммерция разрешена) | Docker на Hetzner CX22 + Caddy (auto-TLS) | Docker там же | Postgres 16 + Redis (AOF) в контейнерах — решение по managed позже |

**Стоимость на старте:** домен ~30 BYN/год · Hetzner CX22 €4–8 · Cloudflare Pages/R2 $0–1 · Neon free / Upstash free (CI) $0 · Resend $0–20 · Sentry/PostHog free → **€5–15/мес**, без платных staging-окружений.

**Бэкапы при self-hosted БД (обязательно до запуска):** `pgbackrest`/`wal-g` → Cloudflare R2 (WAL-архив = PITR), ежедневный дамп, недельный **тест restore на staging-стек**, снапшоты Hetzner. Непроверенный бэкап бэкапом не считается.

**Фри-тиры, проверить лимиты перед использованием:** Upstash считает команды в сутки — блокирующие чтения BullMQ выжигают квоту за часы, поэтому Redis везде свой в контейнере; Vercel Hobby по ToS non-commercial → прод-фронт на Cloudflare Pages; Supabase free-проекты засыпают при неактивности → не годятся под staging.

**CI/CD (GitHub Actions + GHCR + GitHub Environments).**
- **PR:** `lint` → `typecheck` → `vitest` → `build` (кеш Turborepo в GH Actions cache) → `prisma migrate deploy` на Neon-ветку PR → e2e API (Supertest) → Playwright smoke → Lighthouse CI на превью лендинга. Ветка БД удаляется при закрытии PR.
- **merge в `develop`:** сборка образов → push в **GHCR** (тег = `sha`) → SSH на VPS → `docker compose -p staging pull && up -d` → `migrate deploy` → smoke `/health`.
- **тег `v*`:** тот же самый образ (никакой пересборки на релиз) → environment `production` с manual approval → `migrate deploy` → `up -d` → smoke → авто-rollback на предыдущий `sha` при провале хелсчека.
- Секреты — в GitHub Environments раздельно для `staging`/`production`; деплой по SSH deploy-key (не пароль); миграции только аддитивные (expand/contract), чтобы откат кода не ломал БД.

**Переменные окружения (минимум):** `DATABASE_URL`, `DIRECT_URL`, `REDIS_URL`, `JWT_ACCESS_SECRET`, `JWT_REFRESH_SECRET`, `TELEGRAM_BOT_TOKEN`, `TELEGRAM_WEBHOOK_SECRET`, `STORAGE_ENDPOINT/KEY/SECRET/BUCKET`, `RESEND_API_KEY`, `PUBLIC_API_URL`, `PUBLIC_SITE_URL`, `SENTRY_DSN`, `POSTHOG_KEY`.

## 17. Стратегия тестирования

**Unit (Vitest), обязательный минимум:**
- `AvailabilityService`: пустой график; несколько интервалов в день; исключение-выходной; исключение с особыми часами; бронь ровно на границе интервала; буфер после услуги; услуга длиннее остатка интервала; lead time; горизонт; полночь и переход через сутки; год/месяц на границе; корректность зоны `Europe/Minsk` при подстановке фиктивного `now`.
- `BookingStateMachine`: все допустимые и **недопустимые** переходы; отмена клиентом до/после cutoff; истечение `pending`.
- Расчёт рейтинга (среднее опубликованных оценок), нормализация телефона, генерация `slug`.

**Integration/e2e API (Supertest + Testcontainers Postgres):**
- Двойная бронь одного слота в двух параллельных запросах → ровно один 201 и один 409.
- Идемпотентность `POST /bookings` по одному `Idempotency-Key`.
- IDOR: доступ к чужой брони/профилю/фото → 403/404.
- `masterNote` отсутствует во всех клиентских ответах (snapshot-тест DTO).
- Отмена брони снимает задачи напоминаний (проверка через фейковую очередь).

**E2E UI (Playwright, мобильный вьюпорт по умолчанию):**
1. Мастер: регистрация → онбординг → публикация → страница видна по ссылке.
2. Клиент: каталог → фильтр → мастер → бронь → бронь видна в кабинете; слот исчез из выдачи.
3. Мастер: ручная запись из директа → окно занято.
4. Отмена клиентом → мастер видит статус.
5. Отзыв после `completed` → рейтинг в каталоге обновился.

**Нагрузка (k6, перед запуском):** `GET /catalog/masters` 100 RPS, `GET /availability` 50 RPS, 20 параллельных попыток брони одного слота. Цель: p95 <500 мс, 0 двойных броней.

**Ручная матрица устройств:** iPhone SE (маленький экран), iPhone 14/15 (safe-area), Android mid-range Chrome, Telegram in-app browser (важно: мастера будут открывать ссылки из Telegram), Instagram in-app browser (частый источник переходов, часто ломает cookie — проверить логин).

**Smoke-данные (маркеры):** ручные прогоны Postman/curl/Playwright создают реальные записи в БД. Email: `{role}.smoke.{runId}@example.com`; idempotency броней: `smoke:{runId}:…`. Скрипт очистки `pnpm db:cleanup:smoke` — отдельный PR после auth; до него — сброс локальной БД или delete по паттерну. Детали: TECH-DESIGN §29, `.cursor/rules/lumira-smoke-data.mdc`.

## 19. Риски и меры

| Риск | Влияние | Мера |
|---|---|---|
| **Cold start:** пустой каталог → клиенты уходят | критично | Запуск «мастер-first»: 20 мастеров руками до промо для клиентов; мастер приводит своих клиентов личной ссылкой; клиентское промо только после наполнения |
| Мастера продолжают вести записи в блокноте | высокое | Онбординг ≤5 минут, ручная запись в 3 тапа, Telegram-напоминания как немедленная выгода, личная помощь первым 20 мастерам |
| Двойные брони / потерянные записи | критично для доверия | `EXCLUDE`-констрейнт в БД + идемпотентность + нагрузочный тест + аудит `BookingEvent` |
| Напоминание по отменённой брони | среднее, бьёт по доверию | Отмена задач по `jobId` + регрессионный тест + лог `notifications` |
| Блокировка/лимиты Telegram-бота | среднее | Соблюдение лимитов (30 msg/сек), очередь с throttle, email-fallback (v1.1), обработка 403 |
| beautygo.by быстрее наберёт мастеров | высокое | Дифференциация через UX мастера и портфолио-витрину; фокус на конкретных нишах (ногти/брови) и районах, а не «все услуги сразу» |
| Сложность слот-логики съест сроки | высокое | Двойной спринт 3, тесты до реализации, никакого «повторяющегося сложного расписания» в MVP |
| Юридические требования по ПД | среднее | Согласия, политика, экспорт/удаление данных с первого релиза; вычитка юристом до запуска |
| Модерация контента (чужие фото, откровенный контент) | среднее | Ручная модерация в MVP при малых объёмах, хеш-дубликаты, NSFW-скрининг в v1.1, форма жалобы |
| Один разработчик = bus factor | среднее | ADR-документы, тесты, никакой «магии» в коде, инфраструктура как код (Docker Compose + миграции) |
